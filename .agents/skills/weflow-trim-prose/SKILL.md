# 删掉注释和文档里多余和误导的句子

只写现状、写成最终结论、经过写进 issue 和 PR 的规则见 [CLAUDE.md](../../../CLAUDE.md) 的「Wiki」一节，skill 的写法见「Skills」一节，书面措辞和扫描过程性说法的命令见 [weflow-wiki](../weflow-wiki/SKILL.md#写法)。这里是判断一句话该删还是该留的标准，以及把全部注释和文档读一遍的步骤。

## 范围

- 代码注释：Rust 的 `///`、`//!` 和普通注释，WebUI 的 JSDoc 和 CSS 注释，HTML 模板、工作流和脚本里的注释。
- 文档：两份 README、`web/` 的 README、CLAUDE.md、`.agents/skills/` 下的 skill、`.claude/loop.md`、Wiki 的每个页面。
- PR、issue 和提交信息可以写经过和改动前后的对比，那正是它们的用处；但同样不复述对话，见[对话里的内容](#对话里的内容)。

## 要删的

按读者的需要判断：删掉这句以后，改这段代码或照着做的人少知道了什么？什么都没少，就删。常见的有下面几类。

### 复述需求

提需求时的说法、比喻或来源留在了文字里，读者从中得不到系统做什么：

- 「像某产品那样」「as in <产品>」「like the side panel of <产品>」：写这个界面本身是什么样，需求的来源写 issue 号。
- 强调这是有意的：「是正式的数据，不是暂用的」「这是设计如此」。写明它做什么就够了。
- 按谁的要求：「按维护者的要求」「用户希望」。

### 经过和前后对比

文字说的是写下它时发生了什么，不是现在的代码：

- 「as before」「as it did」「原来」「改为」「已删除」「不再」：删掉指向旧行为的部分，只留现状。同一段里指前一步的「as before」（如测试里的上一个断言）不属于这一类。
- 「本次」「这个 PR」「修复后」：注释和文档里没有「这次」。
- 写下时正确、现在已经不成立的说明（写着「不读取其中的内容」，代码却已经读取）：改成现状。

### 排查碰壁后留下的警告和经验

排查时走过的弯路、某一次遇到的现象，写成了给后来者的提醒：

- 试过但不对的方向，如「X 字段可能保存了这个，在 4.x 上是 0」：结论已经写在别处（Wiki 的主题页）时删掉；没写时把结论写进 Wiki，经过留在 issue。
- 只在一次排查里出现、已经修好或不会再遇到的现象：「旧的构建要等 50 秒」、已修复的 bug 的绕过办法、某个工具一次性的故障。
- 泛泛的自我提醒：「凭记忆写的表可能有错」「注意别弄错」。
- 为一次排查写的探针或测试的说明，只交代了当时的用意（「用可写的 TEMP 运行，以区分环境和内容」）：改写成它做什么、输出什么。

### 稻草人

否定一个读者本来不会采用的做法，或者正确的做法已经写明，又补一句反面：

- 「用 `cargo sweep` 清理，不用 `find -delete` 自制清理」：正确的做法已经写了，后半句删掉。
- 「不要手改 X」「不要结束所有 Y 进程」「不是配置的问题」：没有人会这样做，或者是在回应某一次具体的误判。
- 判断方法：被否定的做法是读者顺手就会做的吗？是，而且后果不明显，那是坑，保留并写明后果；不是，就删。

### 计划和过时的引用

- 没有兑现的打算：「for a future standalone binary」「以后会……」。计划写进 issue。
- 依附于已关闭 issue 的说明，如「#N 会有意改掉的基线」：issue 关闭后句子失去意义，删掉或改成现状。
- 引用已经不存在的文件、函数、命令或参数。

## 要留的

下面这些看起来像上面几类，但不删：

- 原因：「不这样做时……会失败」「without X, Y happened」。它说明代码为什么是这样；用了过去时也是原因，不为改时态单独改。
- 会反复遇到的坑：自然的做法在不明显的地方出错（如 `gh pr checks --watch --required` 提前退出），写成「做 X 时会 Y，因此 Z」。
- 规则和约束，包括写成否定句的：隐私、只读、不绕过 ruleset、不联网下载。
- 面向用户的警告和报错的处理办法。
- 其他规则要求写的说明，如探针只打印汇总、不打印聊天内容（见 [weflow-real-account](../weflow-real-account/SKILL.md)）。
- Wiki 里的调研结论、「评估后不采用的方案」表、带微信版本号的实测记录和「命令-API」的版本列表，见 [weflow-wiki](../weflow-wiki/SKILL.md#写法)。
- 界面里的术语和名称：先在代码里核对是不是界面上的叫法，不当成错字改。
- 维护者写的标语和带个人风格的句子（如 Wiki 首页的口号）：不改，列出来交给维护者决定。

## 对话里的内容

注释、文档、PR、issue 和提交信息都只写结果，以及理解结果所需的上下文，不写讨论的经过：

- 不写「用户要求」「按讨论」「维护者说」「我先试了」「前面提到的」。
- 需求和决定的来源写 issue 或 PR 的链接；选择的原因写成原因本身（「排队而不是返回 429，客户端不必重试」），不写是谁、在哪次讨论里决定的。
- 不用讨论中临时起的、仓库里没有的说法和代号。

## 逐条读完

关键词扫描（[weflow-wiki](../weflow-wiki/SKILL.md#写法) 的 `rg` 命令）只能找到有固定说法的经过和对比；复述需求、稻草人和碰壁的经验没有固定的词，只能逐句读。清理全部文字时：

1. 按 [weflow-pr](../weflow-pr/SKILL.md#开始) 建 worktree 和分支；Wiki 在 `wiki/` 里单独改。
2. 在 worktree 里运行 [`scripts/list_comments.py`](scripts/list_comments.py)，列出全部受版本控制的源文件的注释（跳过第三方和生成的文件）。输出分成几份，每份约 64 KiB，一条注释一行，连续的注释行合成一条：

   ```sh
   python .agents/skills/weflow-trim-prose/scripts/list_comments.py temp/comments
   ```

3. 一份一份读完。每读完一份，在 `temp/comments/findings.md` 里记下结果：`文件:行`、原句、删掉还是改成什么、属于哪一类；没有就写「无」。中断后可以接着读，也不会漏掉某一份。
4. Markdown 文件整篇读：CLAUDE.md、README、各个 skill、`.claude/loop.md`、Wiki 的每一页。
5. 同一类句子查遍所有位置后一起改，不逐处停下来问。只改属于上面几类的句子，其他措辞不顺手改，免得改动散到整个仓库。
6. 改完删掉 `temp/comments/`。

## 改的时候

- 只动文字，不动代码。删掉整句或句中的从句后，把这一段重读一遍：语句要通顺，剩下的内容仍要说清这一项做什么。
- 公开项的文档注释不能删空：`missing_docs` 和 `bun run check` 的 JSDoc 检查要求每个公开项、导出项都有说明，删到没有内容时改写成它做什么。
- 契约类型（`weflow-core` 的 `contract/`）的文档注释就是 JSON Schema 的 `description`：改了要重新生成快照和 WebUI 的类型，见 [weflow-contract](../weflow-contract/SKILL.md)。
- 同一句话也写在 Wiki 或另一个 skill 里时，一起改。
- 要删的内容是别处没有的结论时，先把结论补到它该在的地方（Wiki 的主题页、issue），再删。

## 检查和提交

- 改了 Rust 的注释：`cargo fmt --all -- --check`、`make rustdoc`；改了 `web/`：`bun run check`；改了 README、CLAUDE.md 或 skill：`make docs-check`。
- 主仓库的改动按 [weflow-pr](../weflow-pr/SKILL.md) 开 PR，标题用 `docs(<scope>):`，加「文档」标签（见 [weflow-issues](../weflow-issues/SKILL.md)）；Wiki 按 [weflow-wiki](../weflow-wiki/SKILL.md#提交和推送) 提交和推送。
- PR 正文按类列出删了什么、留了什么和留下的理由，方便维护者逐条核对。

## 写新文字时

写的时候就用同样的标准，以后不必再清理：

- 注释写这段代码做什么、为什么这样做（不这样做会怎样），不写怎么发现的、试过什么、改之前是什么样。
- 排查得到的结论有长期价值时写进 Wiki 的主题页（结论 → 依据），经过写进 issue 或 PR。
- skill 的坑只写会反复遇到的；只在一次排查中遇到、已经修好的不写。
- 写完用 weflow-wiki 的扫描命令查一遍，再对照[要删的](#要删的)几类把新增的句子读一遍。
