# Bug 监控 loop

本文件写给负责修 bug 的智能体，只写要做到什么，不绑定具体的平台和工具：循环、定时唤醒、后台任务、子智能体、给其他会话发消息，都用所在平台自己对应的功能来做。

## 启动

用所在平台的循环功能运行下面这项任务，按「节奏」反复执行：

```
监控 issues，出现 Bug 标签的由你来修；收到其他智能体的 Bug 修复请求也由你来修，修完通知对方
```

## 要求

- 监视 `334456777/WeFlow` 上带 `bug` 标签的未关闭 issue（`gh issue list -R 334456777/WeFlow --label bug --state open`），出现就修。
- 其他智能体发来的 bug 修复请求，也由你修，修完通知对方。
- 合并（merge commit）：
  - 从带 `bug` 标签的 issue 修的 bug：开 PR 后直接开启自动合并，CI 全部通过后由 GitHub 合并。
  - 其他智能体委托的修复：合不合并由委托方决定。委托时说了是否自动合并的，照办；没说，或要看到修复结果才能决定的，修完后把修复结果（PR 链接、改了哪些文件、怎么验证的、CI 结果、是否改变了用户可见的行为）发给委托方，问它是否合并，按它的答复合并或留着。
  - 合并后删掉本地分支，看板上的 PR 和 issue 都设为 Done。

## 节奏

- 每 5 分钟查一次。检查在后台一直跑，不用有时限、到期会自己停下的监视方式。
- 另外每 50 分钟左右保底唤醒一次，后台检查中断了也能接着做。
- 修完一个 bug 后，重新开始检查。

## 范围

- 只修 bug。不是 bug 的 issue（增强、WebUI、优化等）留给其他会话。
- 看板只改自己负责的条目。
- 发版（打 tag）必须先问。

## 修复流程

- 在自己的 worktree 和分支（`fix/<scope>-<描述>`）上修，不在共用的工作副本里切换分支。
- 每个 worktree 编译时用自己的 target 目录：`CARGO_TARGET_DIR=<主工作副本>/target/wt-<worktree 名>`。不用 `target/debug`，也不让几个 worktree 共用一个目录，先后修的几个 bug 也不共用。
- 提交：
  - 提交信息和 PR 标题用 `type(scope):` 加中文描述；
  - PR 描述用中文，用 `fixed`、`closed` 关联 issue；
  - 加标签，加入看板并设为 In Review。
- 用户能看到的行为变了，先推送 Wiki，再合并 PR。
- 等 CI 跑完再汇报，不在 CI 还没出结果时结束回合。
- 合并后，主工作副本要 `git pull`，删掉 worktree 和它的 target 目录。

## 同时有多个 bug

同一时间待修的 bug 不止一个时（多个会话发来请求，或扫描到多个带 `bug` 标签的 issue），每个 bug 交给一个子智能体去修，几个子智能体并行。只有一个 bug，或所在平台不能开子智能体时，自己一个一个修。

- 每个子智能体有自己的 worktree，各用一个 `fix/<scope>-<描述>` 分支。
- 交给子智能体的说明要写清楚：
  - issue 链接，或请求方说的原因和建议的修法；
  - 上面「修复流程」和「约束」的要求；
  - 做完的标准：补测试，推送分支，开 PR，加标签，加入看板设为 In Review，回报 PR 链接、改了哪些文件、是否改变了用户可见的行为。
- 子智能体不合并 PR，也不改 Wiki。下面这些由你做：
  - 等 CI；
  - 需要时推送 Wiki；
  - 按上面「要求」里的合并规则合并 PR 或问委托方，合并后删掉分支、worktree 和它的 target 目录；
  - 把看板设为 Done；
  - 通知请求方。
- 两个 bug 要改同一批文件时不并行：先修一个，合并以后再交下一个，避免冲突。
- 一次合并一个 PR：每合并一个就在主工作副本里 `git pull`。后面的 PR 和 main 冲突时，让对应的子智能体 rebase 后重新推送。
- 所有子智能体的 PR 都合并，或已把修复结果交给委托方等它决定之后，再重新开始检查；委托方答复后再合并。

## 约束

- 回复用简体中文。
- 仓库、Project「WeFlow」和 Wiki 都是公开的：不上传聊天记录、wxid、隐私信息、本地路径、密钥、API Key。
- 真实微信数据只读，只报汇总。

## 停止

这个智能体什么时候关由用户决定；新建它的智能体不关它。用户要关时，先停干净再关会话：

1. 停掉后台检查，连同它留下的子进程（如还在等待的 sleep）；
2. 取消保底唤醒；
3. 确认手上没有进行中的修复：没有自己建的 worktree、`fix/*` 分支和开着的 PR；有的话先做完，或告诉用户还剩什么；
4. 回报以上结果，之后不再启动新的检查。
